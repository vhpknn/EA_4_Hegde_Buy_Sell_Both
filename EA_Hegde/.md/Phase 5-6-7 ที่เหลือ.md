ได้ครับ Phase 6 คือ “รันระบบเดิมต่อเนื่องบน Demo” ส่วน Phase 7 คือ “ตรวจหลักฐานรวม แก้เฉพาะปัญหาที่พบ และล็อกเวอร์ชันสุดท้าย” ทั้งสอง Phase ไม่ใช่งานเพิ่มกลยุทธ์ใหม่ครับ 

รายละเอียดด้านล่างเป็นแผนล่วงหน้า ยังไม่สั่งเริ่ม Phase 6 ตอนนี้ เพราะ Phase 5 ยังอยู่ที่ Preflight และยังไม่มีผล Short Test

## Phase 6 — Long Run ข้ามวัน

### 1. เงื่อนไขก่อนเริ่ม

ต้องตรวจผล Short Test ก่อน โดยแยกให้ชัดว่าข้อใดผ่าน ไม่ผ่าน หรือไม่มีหลักฐานครอบคลุม และไม่มีปัญหาร้ายแรงที่ยังควบคุมไม่ได้ เช่น Position ผิดเงื่อนไขหรือ State/ทุนผิดจนเชื่อผลต่อไม่ได้ หากมีต้องจัดขอบเขตแก้และ Retest ก่อนรันยาวครับ 

ข้อมูลตั้งต้นของรอบเรา:

| รายการ | ค่าที่เตรียมไว้ |
|---|---|
| บัญชี | Demo Hedging |
| Symbol | XAUUSD |
| Magic | `99998` |
| Source | `1a3b38f` หากไม่มีชุดแก้ใหม่จาก Short Test |
| Preset หลัก | `LONG_01_OVERNIGHT_DRAFT.set` |
| ReportDays | 1 สำหรับตรวจรอบรายงาน |
| Max Spread | 25 |
| Instance | หนึ่ง EA ต่อ Symbol + Magic |

ถ้า Short Test ทำให้ต้องแก้โค้ด จะใช้ SHA ใหม่ที่ตรวจและ Compile แล้ว ไม่เรียกผลของหลาย Source ว่าเป็นชุดเดียวกันครับ 

### 2. ตรวจความพร้อมของรอบยาว

ก่อนเริ่มจริง ตรวจครั้งเดียวให้ครบ:

1. เลือก `.ex5` จาก Source ชุดที่ยืนยัน
2. โหลด Preset Long Run แล้วตรวจค่าที่โหลดจริง
3. ตรวจว่า Magic `99998` ยังไม่ปน History/State จากงานอื่น
4. ตรวจ Demo Hedging และ Symbol ให้ตรง
5. บันทึกเวลาเริ่มทั้งเวลา Server และเวลาท้องถิ่น
6. เตรียมเก็บ Experts, Journal, History, CSV และภาพเหตุสำคัญ
7. ยืนยันช่วง Session ที่ใช้จริงให้การรันครอบคลุมทั้ง Block/Open

Session ในไฟล์ที่ส่งให้เป็น `01:00–04:00` ตามเวลา Server ต้องใช้เวลา Server ไม่ตีความเป็นเวลาไทยครับ 
### 3. เริ่มรันและรักษาค่าคงที่

เป้าหมายของรอบนี้คือ **ความต่อเนื่อง** ของระบบเดิม:

```text
เริ่มรันด้วย Source และ Preset ที่ล็อก
→ ปล่อยให้ EA ทำงานตาม Gates
→ เก็บเหตุการณ์และหลักฐาน
→ ไม่แก้ Source หรือเพิ่มฟีเจอร์ระหว่างรัน
```

วางแผนประมาณ 24–48 ชั่วโมง แต่เกณฑ์ไม่ได้มีเพียง “เปิดโปรแกรมครบเวลา” ต้องมี Tick, รอบ Basket, Session boundary และโอกาสให้ Report เกิดจริงตามกรณีครับ 

ไม่ต้องส่งผลให้ผมทุกครั้งที่เปิด–ปิด Order เก็บเป็นชุดเดียว ยกเว้นเกิดเหตุผิดปกติร้ายแรง

### 4. สิ่งที่ต้องติดตาม — 8 หมวด

| ID | หมวด | สิ่งที่ต้องมีหลักฐาน |
|---|---|---|
| L01 | หลายรอบ Basket | ไม่มีคู่ใหม่ซ้อนกับ Basket เดิม และไม่เปิดขาที่หายกลับมา |
| L02 | Session | Auto ถูก Block/Open ตามเวลา Server และ Protection ไม่หยุดตาม |
| L03 | Protection | Cut Loss / BE / Trailing / RR ที่เกิดจริงตรงกติกา |
| L04 | State / Restart | State คงอยู่และ Restore ถูกต้องในขอบเขตที่รองรับ |
| L05 | Accounting | Virtual Equity, Closed Net และ Cycle เทียบกับข้อมูลใน Scope ได้ |
| L06 | Report | ถึงกำหนดจริง มีช่วง Basket ว่าง และสร้าง CSV จริง |
| L07 | Connection | เมื่อหลุด/กลับมาจริง มีเวลาและผลกระทบให้ตรวจ |
| L08 | Run Health | ตรวจ Log ซ้ำผิดปกติ ไฟล์ค้าง และ Position ค้างผิดเงื่อนไข |

เหตุที่ไม่เกิดต้องเป็น `NOT_COVERED` ไม่ใช่ `PASS` จากการรันครบชั่วโมงครับ 

กรณี Restart ที่ตั้งใจตรวจต้องเตรียมจังหวะไว้ก่อน และคง Account/Symbol/Magic/Point Digits/Inputs ที่เกี่ยวข้อง ไม่เปลี่ยนหลายอย่างพร้อม Restart แล้วอ้างว่าพิสูจน์ Restore เดิมครับ 

### 5. เหตุที่ไม่ต้องตีความเป็นบั๊กทันที

- Spread มากกว่า 25 แล้วไม่มี Auto Order: อาจเป็นการทำงานของ Spread Gate ตามที่ตั้งไว้
- เหลือ Position ขาเดียวหลังอีกขาปิด: เป็นสถานการณ์ที่กลยุทธ์ปัจจุบันอนุญาตให้ Protection จัดการขาที่เหลือต่อ
- Report ยังไม่เกิดขณะ Basket ไม่ว่าง: ต้องตรวจเงื่อนไขเวลารายงานและ Basket ประกอบ
- RR ปิดก่อน Trailing: ไม่ใช่หลักฐานว่า Trailing เสีย 

ไม่เพิ่ม Spread limit หรือเปลี่ยนกติกากลางรันเพื่อให้เกิด Order มากขึ้นครับ

### 6. เงื่อนไขหยุดก่อนครบเวลา

หยุดรอบและเก็บหลักฐานเมื่อพบ เช่น:

- เปิด Basket ใหม่ทั้งที่ของเดิมยังค้าง
- Exposure ผิดเงื่อนไขและไม่ได้อยู่ในกระบวนการเปิดคู่/Rollback ที่คาดไว้
- SL หายและระบบไม่พยายามจัดการตามกรณี
- State หรือข้อมูลทุนผิดจนเชื่อผลต่อไม่ได้
- ใช้บัญชีหรือ Source ผิดชุด
- มีการเปลี่ยน Source โดยไม่ได้บันทึก 

การหยุดรอบไม่ใช่เพียงปิดโปรแกรมแล้วถือว่า Position จบ ต้องบันทึก Position ที่ยังค้างและวิธีจัดการให้ชัด

### 7. จบรอบและรวบรวมหลักฐาน

เมื่อสิ้นสุดรอบที่วางไว้:

1. บันทึกเวลาจบและเหตุขัดจังหวะทั้งหมด
2. เก็บภาพ Position/Panel และ State ที่จำเป็น
3. รวบรวม Experts + Journal ครอบคลุมช่วงรัน
4. เก็บ History และ CSV
5. เก็บ Preset ที่โหลดจริงและ Source SHA
6. ระบุว่าปลายรอบยังมี Position ค้างหรือไม่

หากสั่งปิดเพื่อจบรอบ ต้องแยกเหตุ “ปิดโดยผู้ทดสอบ” ออกจากการปิดโดยกลยุทธ์ ไม่รวมเป็นหลักฐานว่า Protection ปิดเอง

จุดจบ Phase 6 คือได้ชุดหลักฐาน Long Run พร้อมข้อจำกัดความครอบคลุม ไม่ใช่ประกาศผ่านทั้งหมดทันทีครับ 

## Phase 7 — ตรวจผลรวมและปิดงาน

### 1. ตรวจที่มาของหลักฐานก่อน

รวบรวมผลจากทั้งสองชุด:

```text
SHORT / TESTER
SHORT / DEMO
LONG / DEMO
```

ผมจะตรวจว่าแต่ละชุดตรงกับ Source, Preset, Symbol/Magic และช่วงเวลาที่ระบุ หากคนละเวอร์ชันต้องแยกผล ไม่รวมแล้วเรียกว่าผ่านเวอร์ชันเดียวกันครับ 

คุณไม่ต้องเปิด CSV ไล่ตรวจทุกช่องเอง ผมจะช่วยอ่านหลักฐานและเติม Checklist เป็นรอบรวมตามที่ตกลงไว้

### 2. เติมผล Checklist ตามหลักฐานจริง

ใช้กรณีหลักเดิม 34 กรณี: Short 26 และ Long 8 โดยรายละเอียดของ Patch ล่าสุดอยู่ในรายการย่อยของ Checklist ที่ปรับแล้ว

| ผล | ความหมาย |
|---|---|
| `PASS` | มีหลักฐานตรงเกณฑ์ในขอบเขตที่ระบุ |
| `FAIL` | มีหลักฐานว่าพฤติกรรมไม่ตรงเกณฑ์ |
| `NOT_COVERED` | เหตุไม่เกิดหรือหลักฐานไม่พอ |
| `ENVIRONMENT_BLOCKED` | ดำเนินการไม่ได้เพราะสภาพแวดล้อม |

กรณีผ่านเฉพาะเส้นทางปกติแต่ไม่ได้พิสูจน์เส้นทาง Failure ต้องระบุแยก ไม่สรุปว่าครอบคลุมทั้งหมดครับ 

### 3. แยกสาเหตุของข้อค้นพบ

แต่ละปัญหาจะจัดประเภทเป็น:

- บั๊กโค้ด — พฤติกรรมไม่ตรงข้อกำหนด
- Inputs/Preset — ค่าไม่ตรงกรณีหรือค่าที่ตั้งใจใช้
- สภาพแวดล้อม — ไฟล์ผิดชุด, History ขาด, การเชื่อมต่อ หรือ Broker constraints
- ข้อจำกัดที่ระบุไว้ — เช่น Ticket-change operations ที่ยังไม่รองรับครบ
- หลักฐานไม่พอ — ยังตัดสินไม่ได้ 

จะไม่แก้ Logic เพื่อกลบปัญหาจากไฟล์หรือสภาพแวดล้อมผิด และไม่ขยายกลยุทธ์เพื่อแก้ข้อจำกัดโดยไม่ได้รับคำสั่งใหม่

### 4. หากพบข้อที่ต้องแก้

ทำเป็นชุด ไม่กลับไปวนแก้และเปิด Order หลังทุกจุด:

```text
รวบรวมข้อค้นพบ
→ กำหนดขอบเขตชุดแก้
→ ส่ง Patch ครบไฟล์ที่เกี่ยวข้อง
→ Compile รอบรวม
→ ระบุ Source SHA ใหม่
→ Retest กรณีที่ได้รับผลกระทบ
→ อัปเดตผลจากหลักฐานรอบใหม่
```

ผลที่ผ่านก่อนแก้จะไม่ถูกยกมาเป็นผลผ่านของ Source ใหม่โดยอัตโนมัติ ต้องกำหนดว่าอะไรจำเป็นต้องตรวจซ้ำครับ 

### 5. ล็อกเวอร์ชันและบันทึก Milestone

เมื่อปัญหาที่ต้องแก้ถูกจัดการและผลตรวจครบตามเกณฑ์ที่ตกลงกัน จึงรวบรวม:

- Source SHA สุดท้าย
- ผล Compile
- Preset ที่ใช้จริง
- ผล Short/Long และรายการที่ไม่ครอบคลุม
- ข้อจำกัดที่ยังคงอยู่
- Known Issues หากมี
- ขอบเขต Retest และผลหลังแก้

จากนั้น Commit + Push รวมเมื่อจบ Milestone ไม่ทำหลังแต่ละกรณีทดสอบ การปิดงานต้องอ้างผลตามหลักฐาน ไม่ประกาศว่าไม่มีบั๊กหรือพร้อมใช้เงินจริงเพียงเพราะ Compile ผ่านและรันครบเวลา 



ตอนนี้ข้อมูลและ Preset ของ Phase 6 เตรียมไว้แล้ว ส่วน Phase 7 เป็นงานตรวจผลหลังมีหลักฐาน จึงยังไม่มีอะไรให้แก้โค้ดเพิ่มเพื่อ “เตรียม Phase 7” ล่วงหน้าครับ
