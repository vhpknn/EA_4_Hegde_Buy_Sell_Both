ถ้ากรรมการ Audit ขอ ลิส .md ฟังชั่นการทำงานทั้งหมดของโปรเจค โดย บอกฟังชั่น ไฟล์ และ ไฟล์ที่ใช้ร่วม การทำงานที่หวังผล และอธิบาย ตัวอย่างการทำงานจริง ด้วย XAUUSD ให้เห็นภาพ ของแต่ละฟังชั่น เพื่อ Audit สแกนเช็คได้เข้าใจตรงกันและถูกต้อง ได้มั๊ยครับ


ได้ครับ และควรทำเป็นเอกสาร **Audit** ที่ผูกกับ Source จริง เพื่อให้กรรมการเห็นทั้ง “ชื่อฟังก์ชัน → อยู่ไฟล์ไหน → เรียกใช้อะไร → ควรได้ผลอะไร → ต้องตรวจหลักฐานตรงไหน”

เอกสารชุดนี้ต่างจาก Handoff ที่ทำไปแล้ว: Handoff ใช้รับช่วงงาน ส่วนเอกสาร Function Audit ใช้ตรวจพฤติกรรมและความสัมพันธ์ของโค้ดโดยตรง

## หลักสำคัญเพื่อให้กรรมการเข้าใจตรงกัน

ต้องแยกข้อมูล 3 ชั้น ไม่เขียนรวมกันจนดูเหมือนทุกอย่างผ่านแล้ว:

| ชั้นข้อมูล | สิ่งที่ระบุ |
|---|---|
| ข้อกำหนดที่คาดหวัง | กติกาที่ผู้ใช้ยืนยันว่าระบบต้องทำ |
| การทำงานตาม Source | โค้ดใน Commit ที่ระบุทำอะไรจริง มีเงื่อนไขและข้อจำกัดอย่างไร |
| ผลทดสอบที่สังเกตได้ | Log, Position, State, CSV หรือภาพที่พิสูจน์พฤติกรรมนั้น |

ถ้าข้อกำหนดกับ Source ไม่ตรง ต้องระบุเป็นข้อแตกต่าง ไม่แก้คำอธิบายให้ดูเหมือนโค้ดถูกเสมอ

และคำว่า “ตัวอย่างการทำงานจริงด้วย XAUUSD” ต้องแยกให้ชัด:

- ก่อนมีผลรัน: เป็นตัวอย่างจำลองตามโค้ดและเงื่อนไขที่กำหนด
- หลังมีผลรัน: จึงแนบเหตุการณ์จริงพร้อมเวลา, Ticket, Inputs และหลักฐาน

ตอนนี้ยังไม่มีผล Short/Long ส่งมาให้ตรวจ จึงไม่ควรสร้างตัวอย่าง Log แล้วนำเสนอว่าเกิดขึ้นจริงแล้วครับ

## รูปแบบเอกสารที่เหมาะกับงานนี้

จัดเป็น 3 ไฟล์ `.md` เพิ่มจากชุด Handoff ได้ โดยส่งเป็นข้อความให้คุณ Copy เหมือนเดิม ไม่ต้องใช้ ZIP

### 1. `AUDIT_FUNCTION_INDEX.md`

เป็นสารบัญฟังก์ชันทั้งหมดที่พบจริงใน Source ทั้ง 9 ไฟล์

คอลัมน์หลัก:

```text
Function ID
ชื่อและ Signature
ไฟล์ที่ประกาศ/นิยาม
ประเภท: Lifecycle / Trading / Protection / State / Report / UI / Helper
ผู้เรียกโดยตรง
ฟังก์ชันของโปรเจกต์ที่เรียกต่อ
Native MQL5 API ที่ใช้
Inputs / State ที่เกี่ยวข้อง
Test Case IDs
สถานะหลักฐาน
```

ต้องแยก “เรียกโดยตรง” กับ “อยู่ในเส้นทางเรียกทางอ้อม” เช่น:

```text
OnTick()
→ ProtectOnTick()
→ ClosePositionByTicket()
→ RawPositionClose()
→ OrderSend()
```

ไม่เขียนว่า `OnTick()` เรียก `OrderSend()` โดยตรง เพราะจะทำให้กรรมการไล่โค้ดผิดจุด

ไฟล์ที่ไม่มีฟังก์ชัน เช่นไฟล์ประกาศ Inputs/Enum ต้องแสดงตามจริง ไม่สร้างชื่อฟังก์ชันขึ้นมาให้ครบตาราง

### 2. `AUDIT_FUNCTION_DETAILS.md`

รายละเอียดรายฟังก์ชัน โดยใช้หัวข้อเดียวกันทุกตัว:

```text
1. Function ID และ Signature
2. ไฟล์ที่อยู่
3. หน้าที่
4. ผู้เรียกและไฟล์ที่ใช้ร่วม
5. Inputs / Parameters / State ที่อ่าน
6. เงื่อนไขก่อนทำงาน
7. ลำดับการทำงาน
8. Return Value และผลข้างเคียง
9. ผลคาดหวังตามข้อกำหนด
10. ตัวอย่าง XAUUSD
11. กรณีไม่ทำงาน/ล้มเหลว
12. หลักฐานที่กรรมการควรตรวจ
13. ข้อจำกัดหรือความแตกต่างจากข้อกำหนด
14. Test Case ที่เชื่อมโยง
```

ฟังก์ชัน UI/Helper ก็มีตัวอย่างได้ แต่ไม่ต้องฝืนให้เป็นตัวอย่างเปิด Order เช่น `PName()` อธิบายชื่อ Object บนกราฟ XAUUSD หรือฟังก์ชันสีอธิบายว่าค่าใดแสดงสีอะไร

### 3. `AUDIT_XAUUSD_SCENARIOS.md`

เป็นตัวอย่างการทำงานข้ามหลายไฟล์ เพื่อให้เห็นภาพทั้งระบบ เช่น:

- เปิด Hedge สำเร็จ
- เปิดคู่ไม่ครบและ Rollback
- Cut Loss แล้วเหลือขาเดียว
- Break-even ล็อกกำไรและไม่คลายกลับ
- Armed Trailing และ Restore หลัง Restart
- RR ปิดก่อน Trailing
- ทุนหมดและ REFILL
- Session/Spread/Timeout Block
- Report ครบกำหนดก่อนเปิดรอบใหม่
- CSV เสร็จแต่ State ค้าง แล้วกู้รอบเดิม

แต่ละ Scenario จะอ้างกลับไปที่ Function ID และ Checklist S01–S26/L01–L08 ไม่ต้องให้กรรมการค้นชื่อเองทั้งโปรเจกต์

## ตัวอย่างรูปแบบรายฟังก์ชัน

ด้านล่างเป็นตัวอย่างรูปแบบหนึ่งรายการ ไม่ใช่ลิสฟังก์ชันครบทั้งโปรเจกต์ ผมตรวจสูตรและเส้นทางใน `Hedge1_Protect.mqh` จาก Baseline `9900a1e` แล้วครับ

````markdown
## PROTECT-016 — ProtectOnTick()

### Source reference

Baseline:

9900a1e364b7aac01a8f6e3984ce451f34553259

Signature:

```cpp
void ProtectOnTick()
```

ไฟล์:

EA_Hegde/include/Hedge1_Protect.mqh

### หน้าที่

บริหาร Position ที่มี Symbol และ Magic ตรงกับ EA
โดยเรียงลำดับ:

1. Cut Loss SL
2. RR
3. Armed Trailing TP
4. Break-even

### ผู้เรียกโดยตรง

OnTick() ใน Hedge1.0.mq5

### ฟังก์ชันและไฟล์ที่ใช้ร่วม

ภายใน Protect:

- TrailCleanup()
- GetProfitPoints()
- ModifySL()
- ClosePositionByTicket()
- TrailFind()
- TrailLoadBest()
- TrailUpsert()
- TrailRemove()

ผ่าน Engine:

- RawPositionModify()
- RawPositionClose()

ผ่าน Utils:

- HedgePoint()
- PointsToPrice()

อ่านค่าจาก Inputs
และอ่าน/เขียน Trail State ตามเงื่อนไข

### Scope

จัดการเฉพาะ Position ที่:

- POSITION_SYMBOL ตรงกับ _Symbol
- POSITION_MAGIC ตรงกับ InpMagicNumber

ไม่ใช่การบริหารทุก Position ของทั้งบัญชี

### เงื่อนไขก่อนทำงาน

g_engineReady ต้องเป็น true

### ผลคาดหวัง

- ไม่คลาย SL ที่ป้องกันไว้ดีกว่าแล้ว
- SL ที่หายมีโอกาสเข้าบล็อกติดตั้ง แม้กำไรเลย BE Trigger
- RR มีลำดับตรวจมาก่อน Trailing
- Trailing เริ่มใหม่เมื่อถึง Arm หรือ Restore จาก State เดิม
- เมื่อปิดไม่สำเร็จ ไม่ลบ Best Profit
- BE ขยับ SL เฉพาะทิศที่ดีขึ้น

### ตัวอย่าง XAUUSD — จำลองตาม Source

สมมติ:

- Symbol = XAUUSD
- Buy Fill = 4000.00
- InpPointDigits = 2
- หน่วยราคา 1 Point = 0.01
- Cut Loss = 700 Points
- BE Trigger = 1200 Points
- BE Percent = 20
- BE Step = 100 Points
- Pullback = 500 Points
- RR Percent = 200
- Broker ยอมรับคำสั่งที่ส่งในตัวอย่าง
- ไม่มี Gap/Slippage ที่ทำให้ Fill ต่างจากจุดคำนวณ

ตัวเลขเป็นระยะราคา ไม่ใช่กำไรเงินต่อ Position
ห้ามสรุป P/L เป็น USD โดยไม่ยืนยันรายละเอียดบัญชีและ Symbol

#### A. Cut Loss

ราคา SL พื้นฐานของ Buy:

4000.00 - 700 × 0.01 = 3993.00

หากมี SL ที่ป้องกันไว้ดีกว่าแล้ว
ไม่ควรเลื่อนกลับไป 3993.00 เพื่อคลายความเสี่ยง

#### B. ถึง BE Trigger และ Trailing Arm

เมื่อ Bid = 4012.00:

Profit Points = (4012.00 - 4000.00) / 0.01
              = 1200

Trailing Arm = 700 + 500
             = 1200

RR Target = 1200 × 200%
          = 2400

ดังนั้น:

- ยังไม่ถึง RR
- Trailing เริ่ม Track ที่ Best = 1200
- จุด Pullback แรกตามสูตร = 1200 - 500 = 700 Points
- BE แบบเลื่อนตามคำนวณ Lock = 1200 × 20% = 240 Points
- ราคา BE SL เป้าหมาย = 4002.40

การติดตั้ง SL สำเร็จต้องตรวจผล Broker และค่า SL ที่เกิดจริง

#### C. ย่อต่ำกว่า BE Trigger

ถ้า Best ยังเป็น 1200 และ Bid ย่อลงเป็น 4011.00:

Current Profit = 1100 Points
Pullback = 100 Points

ผลคาดหวัง:

- ยังไม่ครบ Pullback 500
- Cut Loss ไม่คลาย SL จาก 4002.40 กลับไป 3993.00
- ไม่ถือว่าการย่อต่ำกว่า Trigger ยกเลิกการล็อกเดิม

#### D. ทำ Best ใหม่แล้วเกิด Pullback

เมื่อ Bid ขึ้นเป็น 4018.00:

Best = 1800 Points
Trailing Exit ตามสูตร = 1800 - 500 = 1300 Points

เมื่อ Bid ย่อลงเป็น 4013.00:

Current Profit = 1300 Points
Pullback = 500 Points

ผลคาดหวัง:

- เข้าบล็อกพยายามปิดด้วยเหตุ TRAILING-TP
- ถ้าคำสั่งสำเร็จและ Position ไม่เหลือ จึงลบ Trail State
- ถ้าปิดไม่สำเร็จหรือยังเหลือ Position ต้องเก็บ State ไว้

#### E. ถึง RR ก่อนเกิด Pullback

ถ้า Bid ขึ้นถึง 4024.00:

Profit = 2400 Points

RR ถูกตรวจมาก่อน Trailing
จึงพยายามปิดด้วยเหตุ RR ใน Tick นั้น

ไม่ควรตีความว่า Trailing เสียเพียงเพราะ RR ปิดก่อน

### กรณีล้มเหลวที่ต้องตรวจ

- Modify ถูก Broker ปฏิเสธ
- Close ถูกปฏิเสธหรือปิดไม่ครบ
````

## สิ่งที่ต้องเพิ่มเพื่อให้เอกสาร “ครบและสแกนได้”

ก่อนจัดฉบับเต็ม ต้องดึงชื่อและ Signature จาก Source จริงทั้ง 9 ไฟล์ แล้วตรวจความสัมพันธ์การเรียก ไม่ใช้ชื่อจาก Comment หรือความจำเพียงอย่างเดียว

รายการต้องแยกด้วยว่า:

```text
มีนิยามและมีเส้นทางเรียกจริง
มีนิยามแต่เป็น Wrapper/Compatibility ที่ไม่ได้ใช้ในเส้นทางหลัก
เป็น Native MQL5 API ไม่ใช่ฟังก์ชันที่โปรเจกต์สร้าง
เป็นแนวคิดอนาคตที่ยังไม่ได้ Implement
```
