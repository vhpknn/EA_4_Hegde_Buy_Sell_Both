ทั้งสองไฟล์ทำหน้าที่ต่างกัน **TEMPLATE คือ "สมุดแผน" ที่บอกว่าต้องทำอะไร** ส่วน **.py คือ "ผู้ตรวจ" ที่เช็กว่าทำตามแผนจริงหรือไม่** ใช้คู่กันกับ AI โดยให้ AI ทำงานเฉพาะเมื่อมีสองอย่างนี้อยู่ในมือ

## 1. เริ่มใช้ในโปรเจกต์ใหม่

1. สร้างโฟลเดอร์โปรเจกต์ และตั้ง Git (Commit แรกเป็นไฟล์เปล่า)
2. คัดลอก TEMPLATE ไปเป็น `PROJECT.md` แล้วกรอกตามลำดับ: กติกาโปรเจกต์ → เป้าหมายและสิ่งที่ไม่ทำ → สเปกทีละกฎ
3. ให้ AI ถามกลับก่อนเขียนโค้ด ทุกข้อที่ตอบ ให้เขียนลงหัวข้อ "คำถามที่ยังกำกวม" แล้วแก้สเปกให้ชัด
4. คุณอ่านสเปกทั้งหมดและยืนยันเอง เพราะตัวตรวจจะตัดสินตามสเปกที่เขียน ถ้าสเปกผิด ผลผ่านก็ผิดตาม
5. Commit ว่า "สเปกเวอร์ชัน 1" ก่อนเริ่มเขียนโค้ดอะไรทั้งสิ้น

## 2. ใช้ไฟล์ .py

ไฟล์ .py ที่ผมให้เป็น **ตัวอย่างของ Hedge1.4 เท่านั้น** (อ่านรูปแบบ Journal ของ MT5 และตรวจสามกฎ) ไม่ใช่ตัวตรวจสำเร็จรูปสำหรับทุกโปรเจกต์ วิธีใช้:

- โปรเจกต์เดิม: รันตรง ๆ ด้วย `python check_rules_example.py <ไฟล์ Journal>.log` ได้ผล PASS/FAIL พร้อมบรรทัดหลักฐาน
- โปรเจกต์ใหม่: ให้ AI แปลงกฎในสเปกแต่ละข้อ (หนึ่งกฎ = หนึ่งฟังก์ชันตรวจ) โดยใช้ไฟล์นี้เป็นต้นแบบ และบังคับว่า **ต้องเขียนตัวตรวจก่อนเขียนโค้ดหลัก**
- ทดสอบตัวตรวจเอง: ใส่ข้อมูลผิดปลอมเข้าไปแล้วดูว่าตัวตรวจจับได้ ถ้าไม่จับ แปลว่าตัวตรวจยังใช้ไม่ได้
- ก่อนใช้เป็นหลักฐาน Audit: รันกับไฟล์เต็ม ไม่ใช่ข้อมูลชุดเล็ก

## 3. ใช้กับ AI แชทใหม่ ทำอย่างไร

AI แชทใหม่ไม่รู้อะไรเลยจากแชทเก่า ดังนั้นทุกครั้งที่เปิดแชทใหม่ ให้ **แนบสามอย่าง** แล้วสั่งงานหนึ่งเรื่องเท่านั้น:

1. `PROJECT.md` (กติกา + สเปก + ตาราง)
2. ไฟล์ตัวตรวจ `.py` เวอร์ชันล่าสุด
3. รายงานการเบี่ยงเบนหนึ่งข้อ (DEV-xxx) พร้อมบรรทัด Log จริง

ข้อความเริ่มต้นแชท (คัดลอกใช้ได้):

````text
ฉันทำโปรเจกต์ตามเอกสาร PROJECT.md ที่แนบ ให้ปฏิบัติตามกติกาในหัวข้อ 0 อย่างเคร่งครัด
งานรอบนี้: แก้ DEV-___ เพียงข้อเดียว
ข้อกำหนด:
- อ่านสเปกและรายงาน DEV แล้วสรุปความเข้าใจเป็นข้อ ๆ ให้ฉันยืนยันก่อน ยังไม่ต้องเขียนโค้ด
- ถ้าส่วนไหนกำกวม ให้ถามฉัน ห้ามเดา
- หลังฉันยืนยัน ให้แก้เฉพาะไฟล์/ฟังก์ชันตามขอบเขตที่อนุญาต
- ห้ามเพิ่มฟีเจอร์ ห้ามเปลี่ยนรูปแบบ Log ห้ามแตะกฎที่ผ่านแล้ว
- ส่งผลเป็น Diff เฉพาะส่วนที่เปลี่ยน พร้อมบอกว่าแต่ละบรรทัดเกี่ยวกับกฎข้อไหน
- บอกด้วยว่าชุดตรวจข้อไหนควรจะเปลี่ยนผล และข้อไหนต้องไม่เปลี่ยน
````

## 4. ขั้นตอนต่อหนึ่งรอบแก้

1. รันตัวตรวจ → ได้รายการ FAIL → เลือกมาหนึ่งข้อ แล้วกรอกรายงาน DEV
2. Commit สถานะปัจจุบัน แล้วสร้าง Branch ใหม่
3. เปิดแชทใหม่ ส่งสามอย่างตามข้อ 3 รอ AI สรุปความเข้าใจ คุณตรวจว่าตรงหรือไม่
4. AI ส่ง Diff → คุณวางลงโค้ด → รันตัวตรวจ **ทั้งชุด**
5. ผลเป็นไปตามเกณฑ์ผ่าน และข้อที่เคยผ่านไม่ล้ม → รวม Branch และอัปเดตตาราง Traceability
6. มีข้อเก่าล้ม → ย้อนกลับทั้งหมดด้วย Git ไม่แก้ซ้อน แล้วกลับไปปรับรายงานให้ชัดขึ้น
7. แก้ไม่ผ่านเกิน 2 รอบ → หยุด กลับไปทบทวนสเปกกับตัวเอง

## 5. หลักจำง่าย

- **สเปกคือกฎของเกม** AI ไม่มีสิทธิ์ตีความเอง
- **ตัวตรวจคือกรรมการ** ไม่ใช่ AI ไม่ใช่ความรู้สึก
- **หนึ่งแชทต่อหนึ่งปัญหา** เพื่อไม่ให้บริบทเก่าปนกัน
- **ไม่ผ่านต้องย้อนกลับ** ไม่ใช่แก้ทับ

ถ้าแชทใหม่ AI ทำผิดกติกา (เช่น แก้เกินขอบเขต) ให้ตอบกลับว่า "ทำผิดข้อ C-0x ในหัวข้อ 0 ให้ย้อนกลับแล้วทำใหม่ตามขอบเขต" แล้ววางกติกาข้อนั้นให้ดู วิธีนี้ชัดกว่าอธิบายใหม่ทั้งหมดครับ

"การสร้างโปรเจคด้ววิธีนี้ ดีกว่าแบบเดิมยังไงครับ"


ดีกว่าตรงที่เปลี่ยนจาก "ให้ AI เดาว่าอะไรผิดแล้วแก้" เป็น "มีเกณฑ์ที่ตรวจได้ แล้วแก้เฉพาะข้อที่ล้ม" ซึ่งตรงกับสิ่งที่ทำให้โปรเจกต์เก่าของคุณวนไม่จบ

## 1. เทียบแบบเดิมกับแบบใหม่

| ประเด็น | แบบเดิม | แบบใหม่ |
|---|---|---|
| จุดเริ่ม | เขียนโค้ดก่อน แล้วค่อยเห็นปัญหา | เขียนสเปกและกติกาก่อน ยืนยันความเข้าใจตรงกัน |
| ตัวตัดสินว่า "ถูก" | ความรู้สึกของคุณหรือ AI | ตัวตรวจที่ให้ PASS/FAIL พร้อมหลักฐานจาก Log |
| เมื่อพบปัญหา | เล่าอาการให้ AI แล้วให้ไล่หาเอง | ส่งรายงาน: สเปกที่ละเมิด, ค่าที่คาดหวัง, ที่เกิดจริง, บรรทัด Log |
| ขอบเขตการแก้ | AI แก้ได้กว้าง จุดอื่นพังตาม | ระบุไฟล์ที่แก้ได้และกฎที่ห้ามแตะ |
| หลังแก้ | ดูด้วยตาว่า "น่าจะดีขึ้น" | รันชุดตรวจทั้งหมด ข้อเก่าล้มคือย้อนกลับ |
| อาการ Buy ปกติ Sell เพี้ยน | พบช้า ไล่หาเป็นสัปดาห์ | กฎต้องมีหลักฐานทั้งสองฝั่ง ฝั่งที่ขาดจะขึ้น "ยังไม่ทดสอบ" |
| Log | EA เขียนเอง บวมและรบกวนระบบ | ใช้ Log ของ MT5 กับ Python ภายนอก |
| Audit | อธิบายด้วยคำพูด | ตาราง Traceability + หลักฐานดิบ + Hash |

## 2. ทำไมแก้ปัญหา "ยิ่งแก้ยิ่งพัง" ได้จริง

การที่ AI แก้จุดหนึ่งแล้วอีกจุดพังเรียกว่า regression และเป็นผลข้างเคียงที่พบได้บ่อยเมื่อให้ AI แก้โค้ด งานวิจัยเรื่องตัวช่วยเขียนโค้ดแสดงว่าการให้บริบทว่าต้องตรวจเทสต์ใดบ้างช่วยลดอัตรา regression ลงได้มาก  อีกปัญหาคือโค้ดเบี่ยงจากเจตนาเดิมทีละน้อย (intent drift) ซึ่งตรวจพบได้เมื่อเทียบกับข้อกำหนดเดิมเท่านั้น  แบบใหม่ของคุณมีทั้งสองอย่าง คือสเปกที่เป็นเจตนาเดิม และชุดตรวจที่รันซ้ำทุกครั้งหลังแก้ [arxiv](https://arxiv.org/html/2603.17973v1)

หลักปฏิบัติเรื่องการเขียนสเปกก็ชี้ทางเดียวกัน คือบอกพฤติกรรม เกณฑ์ตรวจรับ และสิ่งที่ไม่ทำ แล้วให้คนแก้ไขสเปกที่ AI ร่างให้

## 3. หลักฐานจากโปรเจกต์นี้

ในชุดทดสอบ Short Test ที่เราทำ แบบใหม่ให้ผลที่แบบเดิมให้ยาก:

- แยกได้ว่า F-01 เป็นแค่ Log ซ้ำ ส่วน F-02 มีผลต่อความเสี่ยง (SL ตั้งไม่ได้ชั่วคราว ระยะขาดทุนเกิน 70 Points) แทนที่จะไล่แก้ทุกอย่างที่ดูแปลก
- ตัวตรวจจับ SL ที่ถอยหลังได้เมื่อใส่ความผิดปลอมลงไป และผ่านทั้ง 35 การตรวจกับข้อมูลจริง
- ตรวจเทียบ Baseline 12 รอบได้ตรงทุกตัว

## 4. ข้อเสียที่ต้องยอมรับ

- ใช้เวลาเตรียมก่อนเริ่มมากกว่า ต้องเขียนสเปกและตัวตรวจก่อนมีโค้ด
- สเปกผิดแล้วผ่านก็ผิดตาม คุณต้องอ่านและยืนยันสเปกเองทุกข้อ
- ตัวตรวจต้องดูแลเพิ่มเมื่อสเปกเปลี่ยน และยังจับได้เฉพาะสิ่งที่เขียนกฎไว้
- ไม่ได้ช่วยให้กลยุทธ์ทำกำไร แต่ช่วยให้ EA ทำตามแผนที่คุณกำหนด ซึ่งเป็นเป้าหมายของคุณอยู่แล้ว

โดยรวมคือยอมเสียเวลาช่วงต้นเพื่อไม่ต้องวนกลับมาทำใหม่ซ้ำ ซึ่งสำหรับงานที่ต้องส่ง Audit คุ้มกว่าครับ

-----

"สเปกผิดแล้วผ่านก็ผิดตาม คุณต้องอ่านและยืนยันสเปกเองทุกข้อ  ให้ ai เข้ามาช่วยตรงนี้ได้ยังไง ให้ตรวจและบอกว่าน่าจะผิดตรงใหน ควรแก้ยังไง เหมือนเป็นที่ปรึกษา ได้มั๊ย"

ได้ครับ ให้ AI เป็น "ที่ปรึกษาตรวจสเปก" ได้ และทำได้ดีในบางด้าน แต่ต้องกำหนดบทบาทให้ถูก: AI เป็นฝ่าย **ตั้งข้อสังเกตและเสนอทางแก้** ส่วนคุณเป็นฝ่ายตัดสินว่าอะไรตรงกับเจตนาของคุณ

## 1. AI ช่วยตรวจอะไรได้ดีและไม่ได้

งานวิจัยพบว่า GPT-4 ระบุปัญหาในเอกสารข้อกำหนดและให้คำแนะนำแก้ที่เป็นประโยชน์ได้  แต่คุณภาพขึ้นกับข้อมูลที่ป้อน และต้องมีคนตรวจแก้ในบริบทอีกชั้น [arxiv](https://arxiv.org/pdf/2404.17842.pdf)

| AI ทำได้ดี | AI ทำไม่ได้ (ต้องเป็นคุณ) |
|---|---|
| หาคำกำกวม หน่วยที่หายไป คำที่ตีความได้สองทาง | รู้ว่า "คุณตั้งใจให้เป็นแบบไหน" |
| แยกข้อความรวมหลายเงื่อนไขเป็นหนึ่งกฎต่อหนึ่งข้อ | ตัดสินว่าค่าตัวเลขเหมาะกับกลยุทธ์หรือกฎของโบรกเกอร์ |
| จับกฎที่ขัดกันข้ามหลายข้อ | ยืนยันว่ากฎครบตามที่ผู้ตรวจ Audit คาดหวัง |
| หา "กรณีมุม" ที่สเปกไม่ได้พูดถึง | รับรองว่ากฎถูก ในเชิงธุรกิจ |
| ตรวจว่ากฎตรวจวัดได้จริงหรือไม่ | ทดแทนการทดสอบกับของจริง |

ข้อควรระวัง: ความขัดแย้งระหว่างกฎเป็นสิ่งที่มองเห็นได้ยากเมื่ออ่านทีละข้อ เพราะแต่ละข้ออาจดีสมบูรณ์เมื่ออยู่ลำพัง  จึงควรให้ AI ได้เห็นสเปกทั้งชุดพร้อมกัน [wyzer](https://wyzer.it/blog/three-kinds-of-contradiction-manual-review)

## 2. สิ่งที่ให้ AI ตรวจ (เช็กลิสต์ 6 ด้าน)

เกณฑ์มาตรฐานที่ใช้ตรวจข้อกำหนดคือ ข้อเดียวต้องมีการตีความเดียว, ตรวจวัดได้, ตามรอยได้, หนึ่งข้อหนึ่งเงื่อนไข และจำเป็นจริง  นำมาปรับกับงาน EA ได้ดังนี้ [trace](https://www.trace.space/blog/how-to-write-good-requirements-from-clarity-to-validation)

1. **กำกวม**: คำที่ตีความได้หลายแบบ (เช่น "ย่อกลับ" ย่อจากอะไร นับจากจุดไหน)
2. **หน่วยและทิศทาง**: Points หรือราคา, ปัดขึ้นหรือลง, Buy กับ Sell ใช้เครื่องหมายต่างกันอย่างไร
3. **ตรวจวัดได้**: ทุกกฎต้องมีเกณฑ์ตัวเลขที่ให้ตัวตรวจตอบ PASS/FAIL ได้ [testrigor](https://testrigor.com/blog/how-requirement-reviews-improve-your-testing-strategy/)
4. **ขัดแย้งกัน**: กฎสองข้อสั่งสิ่งตรงข้ามในสถานการณ์เดียวกันหรือไม่
5. **ช่องว่าง/กรณีมุม**: Slippage มาก, ราคากระโดด, SL ตั้งไม่ได้, Restart กลางทาง, ข้อมูลหาย
6. **สมมาตร**: กฎฝั่ง Buy มีคู่ฝั่ง Sell ครบหรือไม่ และตรงข้ามกันจริงหรือไม่

## 3. ขั้นตอนใช้งาน

1. เปิดแชทใหม่ ส่งสเปกทั้งฉบับ แล้วใช้คำสั่งด้านล่าง
2. ให้ AI ตอบเป็นตาราง: ข้อสเปก, ปัญหา, ตัวอย่างสถานการณ์ที่ทำให้เห็นปัญหา, ทางแก้ที่เสนอ, ระดับความมั่นใจ
3. คุณตอบทีละข้อ: ยอมรับ / ปฏิเสธ / ขอปรับ แล้วเก็บคำตอบลงหัวข้อ "คำถามที่ยังกำกวม"
4. แก้สเปกตามนั้น Commit เป็นเวอร์ชันใหม่ แล้วให้ AI ตรวจรอบสองเพื่อดูว่าที่แก้ไปไม่สร้างความขัดแย้งใหม่
5. **เปิดแชทอีกอัน** (หรือใช้ AI คนละตัว) ตรวจซ้ำแบบอิสระ ข้อที่สองแชทเห็นตรงกันคือจุดที่ควรแก้ก่อน

````text
คุณคือที่ปรึกษาตรวจสเปก ไม่ใช่ผู้เขียนโค้ด ห้ามแก้สเปกเอง
ตรวจสเปกที่แนบตาม 6 ด้าน: กำกวม / หน่วยและทิศทาง / ตรวจวัดได้ / ขัดแย้งกัน / ช่องว่างและกรณีมุม / สมมาตรซื้อ-ขาย
ตอบเป็นตาราง: ID ข้อ | ปัญหา | สถานการณ์ตัวอย่างที่ทำให้เห็นปัญหา | ทางแก้ที่เสนอ | ความมั่นใจ (สูง/กลาง/ต่ำ)
เพิ่มส่วน "สิ่งที่ฉันต้องสมมติเพื่อให้ตรวจต่อได้" และ "คำถามที่ต้องถามเจ้าของโปรเจกต์"
ห้ามเดาเจตนา ถ้าไม่แน่ใจให้ตั้งเป็นคำถาม
````

## 4. วิธีเสริมที่ทำให้ตรวจแม่นขึ้น

- **ให้เขียนตัวอย่างตัวเลข**: ให้ AI สร้างตัวอย่างรอบเทรด 5–8 กรณีจากสเปกพร้อมผลที่ควรเกิด เช่น "Buy Fill 4147.92 Slippage 41 → SL คือ?" คุณตรวจแค่ตัวเลขตรงใจหรือไม่ ง่ายกว่าอ่านสเปกตัวอักษร
- **เทียบสเปกกับ Log จริง**: ให้ตัวตรวจ Python รันกับ Log ที่มี แล้วดูว่ากฎข้อไหนไม่เคยถูกกระตุ้น หรือกระตุ้นแล้วผลต่างจากที่สเปกเขียน ซึ่งเป็นสัญญาณว่าสเปกอาจผิดหรือหลุดจากพฤติกรรมจริง
- **แยกข้อที่ AI ไม่แน่ใจ**: ข้อที่ความมั่นใจต่ำ คือข้อที่คุณควรใช้เวลาอ่านเอง ไม่ต้องอ่านทุกข้อด้วยความเข้มเท่ากัน

ทั้งหมดนี้ลดภาระการอ่านของคุณ แต่ไม่ได้ตัดการยืนยันสุดท้ายออก สำหรับงาน Audit ควรบันทึกว่าแต่ละข้อใครตรวจ เมื่อไร และผลเป็นอย่างไรไว้ในตาราง Traceability ด้วยครับ

----------

## 1. Prompt ให้ AI ตรวจสเปก

ใช้ในแชทใหม่ แนบสเปกทั้งฉบับก่อนส่ง แล้วคัดลอกบล็อกนี้ได้เลย

````text
บทบาท: คุณคือที่ปรึกษาตรวจสเปก (Spec Reviewer) ไม่ใช่ผู้เขียนโค้ด และห้ามแก้สเปกเอง
เป้าหมาย: หาจุดที่สเปกอาจถูกตีความผิด ขัดแย้ง ไม่ครบ หรือตรวจวัดไม่ได้ ก่อนที่จะนำไปเขียนโค้ด

ข้อมูลที่ให้:
- สเปกทั้งฉบับ (แนบ)
- เป้าหมายโปรเจกต์: [ใส่ 1-2 ประโยค]
- สิ่งที่ไม่ทำ (Non-goals): [ใส่]
- สภาพแวดล้อม/หน่วย: [ใส่]

กติกา:
1. อ่านสเปกทั้งชุดก่อนตอบ เพราะความขัดแย้งมักซ่อนข้ามหลายข้อ
2. ห้ามเดาเจตนา ถ้าไม่แน่ใจให้เขียนเป็นคำถามถึงเจ้าของโปรเจกต์
3. ทุกข้อสังเกตต้องอ้าง ID ข้อสเปกและยกข้อความต้นทางมาประกอบ
4. ห้ามเสนอฟีเจอร์ใหม่ที่ไม่อยู่ในสเปก
5. ถ้าสเปกข้อใดไม่มีปัญหา ให้เขียนว่า "ไม่พบปัญหา" ไม่ต้องคิดหาเพื่อให้ครบ

ตรวจ 7 ด้านทีละข้อสเปก:
A. กำกวม: คำหรือประโยคที่ตีความได้มากกว่าหนึ่งแบบ
B. หน่วยและทิศทาง: หน่วยขาดหรือสับสน, ปัดขึ้น/ลง, เครื่องหมายของฝั่งซื้อและฝั่งขาย
C. ตรวจวัดได้: มีเกณฑ์ตัวเลขที่ทำให้ตัวตรวจตอบ PASS/FAIL ได้หรือไม่
D. หนึ่งข้อหนึ่งเงื่อนไข: ข้อไหนรวมหลายเงื่อนไขและควรแยก
E. ขัดแย้งกัน: กฎสองข้อขึ้นไปสั่งสิ่งตรงข้ามในสถานการณ์เดียวกัน
F. ช่องว่าง/กรณีมุม: สถานการณ์ที่สเปกไม่พูดถึง เช่น ค่ากระโดดแรง, คำสั่งถูกปฏิเสธ, รีสตาร์ตกลางทาง, ข้อมูลหาย, เงื่อนไขสองอย่างเกิดพร้อมกัน, ค่าตรงขอบเกณฑ์พอดี
G. สมมาตร: ทุกกฎของฝั่งหนึ่งมีกฎคู่ของอีกฝั่งครบและตรงข้ามกันจริงหรือไม่

รูปแบบคำตอบ:
ส่วน 1: ตารางข้อสังเกต
| ID ข้อ | ด้าน (A-G) | ข้อความต้นทาง | ปัญหา | สถานการณ์ตัวอย่างที่ทำให้เห็นปัญหา | ทางแก้ที่เสนอ (ร่างข้อความใหม่) | ความมั่นใจ (สูง/กลาง/ต่ำ) |
ส่วน 2: ตัวอย่างตัวเลข 6-8 กรณี จากสเปกปัจจุบัน
  แต่ละกรณี: ข้อมูลเข้า → ผลที่สเปกบังคับ (คำนวณทีละขั้น) เพื่อให้เจ้าของโปรเจกต์ตรวจว่าตรงใจหรือไม่
  ต้องมีกรณีที่ฝั่งซื้อและฝั่งขายคู่กัน และกรณีตรงขอบเกณฑ์อย่างน้อย 2 กรณี
ส่วน 3: สิ่งที่คุณต้องสมมติเพื่อตรวจต่อ (ระบุเป็นข้อ)
ส่วน 4: คำถามที่ต้องถามเจ้าของโปรเจกต์ (เรียงตามความสำคัญ)
ส่วน 5: สรุปจำนวนข้อที่พบปัญหาแต่ละด้าน

ก่อนส่ง ให้ตรวจคำตอบตัวเองอีกรอบ: มีข้อสังเกตข้อไหนที่เกิดจากการเดาเจตนาหรือไม่ ถ้ามีให้ย้ายไปส่วนคำถาม
````

เมื่อได้คำตอบ ให้ตอบทีละข้อว่า ยอมรับ / ปฏิเสธ / ปรับ พร้อมเหตุผลสั้น ๆ แล้วเปิดแชทใหม่อีกอันส่งสเปกฉบับแก้ไปตรวจซ้ำ ข้อที่สองแชทเห็นตรงกันควรแก้ก่อน

## 2. วิธีเขียนสเปกไม่ให้ AI ตีความผิด

ข้อกำหนดที่ดีต้องตีความได้แบบเดียว ตรวจวัดได้ และหนึ่งข้อหนึ่งเงื่อนไข  ข้อกำหนดกำกวมคือข้อที่คนอ่านต่างกันตีความได้ต่างกัน  หลักเขียนที่ใช้ได้จริง: [trace](https://www.trace.space/blog/how-to-write-good-requirements-from-clarity-to-validation)

1. **หนึ่งข้อหนึ่งเงื่อนไข**: อย่าใช้ "และ/แล้ว/หรือ" ผูกหลายพฤติกรรมในประโยคเดียว
2. **ตัวเลขพร้อมหน่วยและทิศทางเสมอ**: ระบุ Points หรือราคา, ฝั่งซื้อและขายแยกกัน, ปัดขึ้นหรือลง
3. **ใช้คำคงที่**: ตั้งอภิธานศัพท์ (เช่น "Fill", "Best", "ล็อก") แล้วใช้คำเดิมทุกที่ ห้ามสลับคำที่หมายถึงสิ่งเดียวกัน
4. **ระบุตัวกระตุ้น เงื่อนไข และผลลัพธ์**: เมื่อเกิดอะไร ภายใต้เงื่อนไขใด ระบบต้องทำอะไร
5. **ระบุกรณีล้มเหลว**: ถ้าทำไม่ได้ต้องทำอะไร (ลองซ้ำกี่ครั้ง, รอนานเท่าใด, หยุดหรือไม่)
6. **ใส่ตัวอย่างตัวเลขต่อกฎ**: อย่างน้อยหนึ่งกรณีปกติและหนึ่งกรณีตรงขอบ
7. **เขียน "สิ่งที่ไม่ทำ" ควบคู่**: บอกขอบเขตเพื่อไม่ให้ AI เติมฟีเจอร์เอง 
8. **ระบุลำดับความสำคัญเมื่อกฎชนกัน**: เช่น กฎความปลอดภัยชนะกฎอื่นเสมอ

แม่แบบหนึ่งกฎ:

````text
ID: R-____-__
ชื่อ: ____
ตัวกระตุ้น (เมื่อ): ____
เงื่อนไข (ถ้า): ____
การกระทำ (ให้ทำ): ____
ค่า/หน่วย/ทิศทาง: ____   (ฝั่งซื้อ: ____ | ฝั่งขาย: ____)
กรณีล้มเหลว: ____
ตัวอย่างปกติ: ข้อมูลเข้า ____ → ผลที่ถูกต้อง ____
ตัวอย่างตรงขอบ: ข้อมูลเข้า ____ → ผลที่ถูกต้อง ____
ลำดับเมื่อชนกับกฎอื่น: ____
เกณฑ์ตรวจรับ (PASS เมื่อ): ____
ไม่รวมในกฎนี้: ____
````

ตัวอย่างการเขียนที่ต่างกัน:

| แบบกำกวม | แบบชัดเจน |
|---|---|
| "ตั้ง Stop Loss ให้พอเหมาะหลังเปิดออเดอร์" | "หลังได้ราคา Fill ให้ตั้ง SL ห่างจากราคา Fill 70 Points ในทิศทางขาดทุน (Buy: ต่ำกว่า, Sell: สูงกว่า) ภายใน 1 วินาที ถ้าตั้งไม่สำเร็จให้ลองซ้ำไม่เกิน 3 ครั้ง แล้วปิดตำแหน่งด้วยราคาตลาด" |
| "ล็อกกำไรเมื่อกำไรพอควร" | "เมื่อกำไรถึง 120 Points ให้ย้าย SL มาล็อก 20% ของกำไรที่ปัดลงเป็นผลคูณของ 10 Points เช่น กำไร 125 → ล็อก 24 Points" |

ตัวอย่างข้างบนเป็นค่าสมมติเพื่ออธิบายรูปแบบการเขียนเท่านั้น (ส่วนวิธีจัดการเมื่อตั้งไม่สำเร็จเป็นเรื่องที่คุณต้องตัดสินใจเอง)

## 3. ลำดับที่ใช้ร่วมกัน

1. คุณเขียนสเปกฉบับร่างตามแม่แบบ
2. ใช้ Prompt ในหัวข้อ 1 ให้ AI ตรวจ ตอบรับ/ปฏิเสธ/ปรับ
3. ให้ AI ตรวจซ้ำในแชทใหม่ แล้วแก้ จนกว่าข้อสังเกตสำคัญหมด
4. คุณอ่านตัวอย่างตัวเลขในส่วน 2 ของคำตอบ ถ้าตัวเลขตรงใจทุกกรณี ถือว่าเข้าใจตรงกัน
5. Commit เป็นสเปกเวอร์ชันที่ยืนยันแล้ว ค่อยเริ่มเขียนตัวตรวจและโค้ด

สังเกตว่าข้อสุดท้าย AI ตั้งความมั่นใจ "ต่ำ" เพราะเป็นเรื่องที่ต้องให้คุณเลือก คุณจึงใช้เวลาอ่านเฉพาะข้อพวกนี้ ส่วนข้อมั่นใจสูงผ่านได้เร็ว

คุณแก้ `PROJECT.md` ตามแม่แบบหนึ่งกฎ ใส่ตัวอย่างปกติและตัวอย่างตรงขอบ แล้ว Commit `v0.2 สเปกหลังรีวิวรอบ 1`

## ขั้นที่ 5: ตรวจซ้ำ แล้วล็อกสเปก

1. เปิดแชทใหม่อีกอัน ส่งสเปก v0.2 พร้อม Prompt เดิม
2. รอบนี้ AI พบข้อใหม่หนึ่งข้อ: กฎ "ลองสูงสุด 3 ครั้งใน 2 วินาที" กับกฎ "ปิดขาถ้าเปิดไม่สำเร็จ" อาจชนกันตอนเวลาเกือบเท่ากัน คุณกำหนดลำดับความสำคัญ แล้ว Commit `v0.3`
3. รอบสามไม่พบข้อสังเกตระดับสูง ปิดสเปก: Commit และ Tag `spec-v1.0`

จากนั้นค่อยเริ่มงานเขียนโค้ด โดยเรียงลำดับดังนี้:

```text
งานที่ 1: เขียนตัวตรวจ Python ของ R-CUT-01 → รันกับข้อมูลปลอมให้ FAIL ก่อน
งานที่ 2: เปิดแชทใหม่ แนบ PROJECT.md + ตัวตรวจ สั่งให้เขียนเฉพาะฟังก์ชันเปิดคู่ + ตั้ง SL
งานที่ 3: รันบน Demo → ตัวตรวจให้ PASS/FAIL → ถ้า FAIL ทำรายงาน DEV ส่งแชทใหม่
```

" ช่วยแนะนำวิธีปรับเทมเพลตนี้ให้เข้ากับโปรเจคอื่นที่ไม่ใช่ EA"


โครงเทมเพลตใช้กับโปรเจกต์อื่นได้เกือบทั้งหมด เพราะหลักคิดไม่ผูกกับ EA คือ **มีสเปกที่ตรวจวัดได้ → มีตัวตรวจอัตโนมัติ → มีหลักฐาน → แก้ทีละข้อ** ที่ต้องเปลี่ยนมีแค่ "หน่วยของกฎ" "แหล่งหลักฐาน" และ "ตัวตรวจ" สามอย่างนี้

## 1. ส่วนที่ใช้ได้ทันที ไม่ต้องแก้

- กติกาโปรเจกต์ (หนึ่งการแก้หนึ่ง Finding, ห้ามเพิ่มฟีเจอร์นอกสเปก, ข้อเก่าล้มต้องย้อนกลับ)
- Non-goals, คำถามที่ยังกำกวม, ตาราง Traceability
- แม่แบบรายงานการเบี่ยงเบน และวงจรทำงานต่อหนึ่งงาน
- บันทึกการเปลี่ยนแปลง และเช็กลิสต์ก่อนส่งตรวจ

## 2. ส่วนที่ต้องปรับตามชนิดโปรเจกต์

| ส่วนของเทมเพลต | EA | เว็บ/แอป | API/บริการหลังบ้าน | งานข้อมูล/Pipeline |
|---|---|---|---|---|
| ตัวกระตุ้นของกฎ | ราคา/เวลา/คำสั่ง | ผู้ใช้กดหรือกรอก | คำขอ (Request) | ไฟล์เข้า/ตารางเวลา |
| รูปแบบเขียนกฎ | ตัวกระตุ้น-เงื่อนไข-การกระทำ | Given / When / Then | สัญญา API (OpenAPI) | ข้อมูลเข้า → ข้อมูลออก + กฎคุณภาพ |
| หน่วย/ทิศทาง | Points, Buy/Sell | วินาที, พิกเซล, สิทธิ์ผู้ใช้ | สถานะ HTTP, ชนิดข้อมูล | ชนิดคอลัมน์, เขตเวลา, ปัดเศษ |
| หลักฐานดิบ | Log ของ MT5 + ประวัติดีล | Log เซิร์ฟเวอร์, ผลรันเบราว์เซอร์, ภาพหน้าจอ | Log คำขอ/ตอบกลับ | ไฟล์ผลลัพธ์, ตารางก่อน/หลัง |
| ตัวตรวจ | สคริปต์ Python อ่าน Journal | ชุดทดสอบอัตโนมัติของหน้าจอ | Contract test เทียบกับสเปก | สคริปต์ตรวจจำนวนแถว/ค่าว่าง/ผลรวม |
| กรณีมุมที่ต้องถาม | Slippage, Invalid stops, รีสตาร์ต | ใส่ข้อมูลผิด, เน็ตหลุด, สิทธิ์ไม่พอ | Timeout, ซ้ำคำขอ, ข้อมูลไม่ครบ | ไฟล์ว่าง, ข้อมูลซ้ำ, Schema เปลี่ยน |
| เกณฑ์ "สองฝั่ง" (C-01) | Buy และ Sell | ผู้ใช้ทั่วไปและผู้ดูแล | สำเร็จและล้มเหลว | ข้อมูลปกติและข้อมูลเสีย |

## 3. วิธีเขียนกฎตามชนิดโปรเจกต์

**เว็บ/แอป** ใช้รูปแบบ Given/When/Then ซึ่งแยกบริบท การกระทำ และผลลัพธ์ชัดเจน  เช่น "Given ตะกร้าว่าง, When ผู้ซื้อกดชำระเงิน, Then ระบบแสดงข้อความผิดพลาดและไม่เข้าขั้นชำระ"  แต่ละเกณฑ์ควรเป็นข้อความเดี่ยวและใช้คำศัพท์ที่นิยามไว้ตายตัวทั้งโปรเจกต์ [qase](https://www.qase.io/blog/acceptance-criteria/)

**API** ให้ถือไฟล์ OpenAPI เป็นสเปกกลางที่ทั้งสองฝั่งยึดถือ และใช้ Contract test ตรวจว่าระบบจริงตอบสถานะ ชนิดเนื้อหา และ Schema ตรงกับที่สเปกสัญญา  ควรเก็บไฟล์สัญญาไว้ใน Git ร่วมกับโค้ด และรันตรวจใน Pull Request  ในกรณีนี้ "เกณฑ์ตรวจรับ" ของแต่ละกฎ คือชื่อ Endpoint + สถานะที่ต้องได้ + Schema ที่ต้องตรง [apideck](https://www.apideck.com/blog/openapi-testing)

**Pipeline/งานข้อมูล** เขียนกฎเป็นคู่ "ข้อมูลเข้าตัวอย่าง → ข้อมูลออกที่ถูก" และกฎคุณภาพที่ตรวจเป็นตัวเลขได้ เช่น จำนวนแถวต้องเท่ากับต้นทาง, ผลรวมคอลัมน์ยอดเงินต้องตรงกัน, ห้ามมีค่าว่างในคอลัมน์สำคัญ

## 4. ขั้นตอนปรับเทมเพลตให้โปรเจกต์ใหม่

1. คัดลอกเทมเพลตเป็น `PROJECT.md` และเปลี่ยนหัวข้อ "สภาพแวดล้อมและหน่วย" ให้เป็นของโปรเจกต์ใหม่ (ภาษา, เฟรมเวิร์ก, เขตเวลา, หน่วยเงิน, เวอร์ชันซอฟต์แวร์)
2. เลือกรูปแบบกฎที่เหมาะ แล้วเปลี่ยนคอลัมน์ในตารางสเปกตามตารางข้างบน
3. แก้ C-01 ให้ตรงชนิดงาน เช่น "ทุกกฎต้องมีหลักฐานทั้งกรณีสำเร็จและล้มเหลว"
4. ระบุว่า "หลักฐานดิบ" ของโปรเจกต์คืออะไร และเก็บอย่างไร (ที่เก็บ, Hash, ห้ามแก้)
5. เลือกวิธีตรวจ แล้วให้ AI สร้างตัวตรวจเริ่มต้นจากสเปก ไม่ใช่จากโค้ดที่มีอยู่
6. ใช้ Prompt ตรวจสเปกเดิมได้ แต่แก้ด้าน B และ F ในรายการตรวจให้เป็นหัวข้อของโปรเจกต์ใหม่ เช่น แทนที่ "Buy/Sell" ด้วย "บทบาทผู้ใช้" แทนที่ "Slippage" ด้วย "Timeout/ข้อมูลไม่ครบ"

ตัวอย่างการแปลงกฎเดียวกันเป็นสามโปรเจกต์ (ค่าเป็นสมมติ):

```text
EA:      เมื่อ Fill แล้ว ตั้ง SL ห่างจาก Fill 70 Points ภายใน 1 วินาที
เว็บ:    Given ผู้ใช้กรอกรหัสผ่านผิดครบ 5 ครั้ง / When กดเข้าสู่ระบบอีกครั้ง / Then ระบบล็อกบัญชี 15 นาที
API:     POST /login ด้วยรหัสผิดครั้งที่ 6 ต้องตอบ 429 พร้อมฟิลด์ retry_after เป็นจำนวนเต็มวินาที
```

## 5. สิ่งที่ต้องระวังเมื่อย้ายโปรเจกต์

- ตัวตรวจต้องมาก่อนโค้ดเสมอ ถ้าไม่มีวิธีตรวจอัตโนมัติ ให้เขียนวิธีตรวจด้วยมืออย่างละเอียดเป็นขั้นตอนแทน และบันทึกผลทุกครั้ง
- งานที่ผลลัพธ์เป็น "ความรู้สึก" (หน้าตา, ความสวย) ตรวจด้วยตัวเลขยาก ให้เขียนเกณฑ์เป็นข้อเท็จจริงที่ดูได้ เช่น ขนาดฟอนต์, สีตามคู่มือ, ระยะห่าง
- ถ้าโปรเจกต์ใหญ่ ให้แบ่งเป็นโมดูล แยกเอกสารสเปกและตัวตรวจต่อโมดูล แล้วมีตาราง Traceability รวมหนึ่งฉบับ
- ถ้าบอกผมชนิดโปรเจกต์จริงที่จะทำ (เช่น เว็บ API หรือ Pipeline) ผมจะร่างเทมเพลตที่ปรับคอลัมน์และกติกาให้ตรงงานนั้นต่อให้ครับ
