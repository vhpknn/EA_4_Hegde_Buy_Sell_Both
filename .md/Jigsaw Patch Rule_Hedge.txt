
โปรเจคสร้าง EA เพื่อแข่งขัน เป้าหมาย เพื่อพัฒนา EA ให้มีประสิทธิภาพ ทำงานได้ตามฟังชั่นที่กำหนด ไม่มีบั๊ก กรรมการ Audit จะตรวจสแกนแบบละเอียด ถ้าพบ บั๊ก หรือ การทำงานไม่ตรงเงื่อนไขเกิน 3 จุด  จะตกรอบทันที

กฎระเบียบและข้อกำหนด (Development & Quality Assurance Rules) 
## 1. วัตถุประสงค์และเป้าหมายหลัก (Objective & Scope)
- **เป้าหมาย:** พัฒนา EA Hedge1.0 ให้ผ่านเกณฑ์การ Audit 100% ไร้บั๊ก และทำงานตรงตามสเปกเป๊ะๆ
- **เกณฑ์คัดออก (Zero Tolerance):** ห้ามมีข้อผิดพลาดร้ายแรง (Critical Bug) และห้ามมีฟังก์ชันทำงานไม่ตรงตามเงื่อนไขสะสมเกิน 3 จุดเด็ดขาด (เกินตกรอบทันที)

## 2. กฎการเขียนโค้ดและการตรวจสอบความถูกต้อง (Coding & Logic Compliance)
- **Logic ตรงตาม Blueprint:** ทุกฟังก์ชัน (เช่น Virtual Capital, Auto-Lot, Session, Break-even,) ต้องเขียนโค้ดให้ทำงานตรงตามเงื่อนไขที่กำหนดไว้ทุกประการ ห้ามมีข้อยกเว้น
- **Null & Error Handling:** โค้ด MQL ทุกบรรทัดต้องมีการดักจับ Error (เช่น เช็คค่า `GetLastError()`, ตรวจสอบพอยน์เตอร์หรือออเดอร์ว่าง) ป้องกันบอทแครชหรือค้างระหว่างรันเทส
- **State Management:** สถานะของบอท (เช่น ตอนติดบล็อก Rollover หรือช่วง Basket ว่างรอเปิดรอบใหม่) ต้องสอดคล้องกับหน้า UI Panel ที่แสดงผลแบบเรียลไทม์ ห้ามตัวเลขกับหน้าจอสวนทางกัน

## 3. ขั้นตอนการตรวจสอบก่อนส่งมอบ (Pre-Audit Testing Protocol)
ก่อนให้กรรมการสแกน ทีมเราต้องผ่านกระบวนการคัดกรอง 3 ชั้นนี้ก่อนเสมอ:
- **Unit Testing:** เทสทีละฟังก์ชันแยกย่อย (เช่น ลองกดปุ่ม Refill, ลองเทสช่วงเวลา Session, ลองเช็คสเปรดเกินลิมิต) ว่าลั่นคำสั่งถูกต้องไหม
- **Stress & Edge Case Testing:** จำลองสถานการณ์ตลาดตึงๆ เช่น ข่าวแรงสเปรดถ่าง, เน็ตหลุดระหว่างเปิดออเดอร์, หรือเหตุการณ์รอยต่อวัน (Rollover) ว่าบอทรอดไหม
- **Code Review & Static Analysis:** ให้คนในทีมช่วยกันนั่งไล่โค้ดทีละบรรทัดเทียบกับ Blueprint เพื่อหาจุดที่อาจทำงานไม่ตรงเงื่อนไข (ลบจุดเสี่ยงให้เหลือ 0 ก่อนส่งตรวจจริง)

## 4. มาตรการจัดการข้อผิดพลาด (Bug Resolution Protocol)
- ถ้าระหว่างรันเทสภายใน พบจุดที่ทำงานไม่ตรงเงื่อนไขหรือบั๊ก แม้จะเป็นจุดเล็กๆ ต้องบันทึกเข้า Bug Tracker ทันที
- จัดลำดับความเร่งด่วน (Priority) และแก้ไขให้จบภายใน 24 ชั่วโมง พร้อมเขียน Unit Test ซ้ำเพื่อยืนยันว่าแก้หายขาด


## กฎเหล็กข้อที่สำคัญที่สุด: ระบบ Mirror & Dual-Side Synchronization (ความสอดคล้องและการทำงานคู่ขนาน 100%)

- **Mirror Execution Symmetry (ความสมมาตรในการออกคำสั่ง):** 
  - ทุกคำสั่งของฝั่ง Buy และ Sell (เช่น การเปิดไม้, การคำนวณ Lot จาก Virtual Capital, การเปิดไม้ Hedge, และการขยับ Break-even) ต้องทำงานภายใต้เงื่อนไขเดียวกันแบบเงาตามตัว (Mirror)
  - ห้ามเกิดเหตุการณ์ที่ฝั่งหนึ่งทำงานตามโปรแกรมปกติ แต่อีกฝั่งเกิดอาการดีเลย์, คำสั่งค้าง, หรือถูกขัดขวางจนปิด/เปิดออเดอร์ไม่ตรงตามเงื่อนไขเด็ดขาด
- **Tolerance = 0 Points (ความคลาดเคลื่อนต้องเป็นศูนย์):** 
  - การคำนวณระยะพอยน์ต์ (Points) ทั้งจุดเปิดไม้ Hedge, จุดตัดขาดทุน (Cut Loss), และจุดล็อกกำไร (TP / Break-even) ต้องแม่นยำ 100% ตรงตามค่าพารามิเตอร์ที่ตั้งไว้ ห้ามมีส่วนต่างหรือความคลาดเคลื่อนแม้แต่ 1 Point เดียว
- **Atomic Operation & Basket Integrity (ความสมบูรณ์ของชุดคำสั่ง):** 
  - การจัดการกลุ่มออเดอร์ (Basket) ทั้งฝั่ง Buy และ Sell ต้องถูกควบคุมด้วยฟังก์ชันเดียวกัน หากเกิดเงื่อนไขปิดออเดอร์ (เช่น ชน TP, Break-even, หรือกดปุ่ม Close Order) ระบบต้องทำการปิดหรือจัดการทั้งสองฝั่งพร้อมกันในรอบประมวลผลเดียว (Tick เดียวกัน) เพื่อป้องกันการเหลื่อมล้ำของสถานะพอร์ต





### 🎯 CORE RULES (ปรัชญาการทำงานหลัก)
1. **เป้าหมายคือการสร้างระบบที่แยกฟังก์ชันออกเป็นไฟล์ย่อยๆ เหมือน "ชิป IC อิเล็กทรอนิกส์" (1 ไฟล์ = 1 หน้าที่) เพื่อให้แก้ไขง่าย ไม่กระทบส่วนอื่น และประหยัด Token
2. **หาทางลัด ทำให้ง่ายที่สุด:** หากเจอไฟล์หรือโจทย์ซับซ้อน ให้หาทางลัดที่เร็วที่สุด
3. **อธิบายเรื่องยากให้ง่าย:** User ไม่ถนัด Coding ให้เปรียบเปรยและอธิบายด้วยภาษาที่เข้าใจง่าย ห้ามใช้ศัพท์เทคนิคซับซ้อนโดยไม่อธิบาย
4. **ทำทีละส่วน & เห็นผลบนเว็บก่อน:** ลุยทำทีละชิ้น ตรวจสอบผลลัพธ์บนเบราว์เซอร์ให้ผ่าน แล้วค่อยไปต่อขั้นถัดไป
5. **แก้เฉพาะปัญหาที่เกิดจริง:** ไม่ต้องเผื่อ Logic ซับซ้อนที่ไม่ได้สั่ง

### 🚨 WORKFLOW RULES (ขั้นตอนการทำงาน)

**ขั้นที่ 1: ปรึกษาและวางแผน (Consultation & Planning Phase)**
- อธิบายการทำงานจากโจทย์/ไฟล์ `.md` ให้เข้าใจง่ายๆ ก่อน
- แสดง **Folder Tree** โครงสร้างไฟล์ใหม่ที่จะสร้าง/แก้ไข และระบุตำแหน่ง Path ให้ชัดเจน
- ระบุว่าแต่ละไฟล์มี **Function/Component** อะไรอยู่ข้างในบ้าง
- 🛑 **หยุดรอจนกว่า User จะพิมพ์คำสั่งว่า "เริ่มงาน" ถึงจะเริ่มส่ง Code ได้**

**ขั้นที่ 2: การส่งมอบ Code (Execution Phase)**
เมื่อได้รับคำสั่ง "เริ่มงาน" ให้ส่ง Code ตามเงื่อนไขต่อไปนี้อย่างเคร่งครัด:

1. **กรณีสร้างไฟล์ใหม่ (New File):** 
   - ส่ง **Full Code** ของไฟล์นั้นๆ เพื่อให้ User นำไปประกอบเหมือนจิ๊กซอว์ทีละชิ้น
   - ระบุ **Path ตำแหน่งที่อยู่ของไฟล์** ให้ครบถ้วนชัดเจนเสมอ

2. **กรณีแก้ไขไฟล์ที่มีอยู่แล้ว (Existing File / Fix Error):**
   - ⚠️ **ห้ามส่ง Full Code เด็ดขาด!** (จนกว่า User จะพิมพ์คำว่า "ขอ fullcode")
   - ให้ส่งเฉพาะโค้ดจุดที่มีปัญหาด้วย **Jigsaw Patch Rule (FIND: / REPLACE:)** เท่านั้น เพื่อให้ User นำไป คัดลอก/วาง ใน VS Code ได้เป๊ะ ไม่หลุด ไม่ซ้ำ ไม่พัง

### 🧩 JIGSAW PATCH RULE (รูปแบบการส่ง Code แก้ไข)

ระบุตำแหน่ง คัดลอก/วาง ให้ชัดเจนที่สุด เพื่อป้องกันปีกกาซ้ำ, Tag ซ้ำ หรือโค้ดเดิมเสียหาย โดยใช้รูปแบบนี้เท่านั้น:

FIND:
```text
[โค้ดเดิมที่มีอยู่แล้วในไฟล์ของ User]

REPLACE:
Plaintext
[โค้ดใหม่ที่แก้ไขแล้ว นำไปวางแทนที่]
